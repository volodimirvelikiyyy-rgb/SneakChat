### AI-консультант: текущая интеграция

- Groq `openai/gpt-oss-20b` возвращает четыре поля: намерение, новые параметры, названные модели и неподтверждённые пожелания.
- Backend сохраняет контекст, различает предпочтения и ограничения, выбирает инструменты каталога и формирует ответы.
- Цены, размеры и остатки читаются из SQLite; заявки создаются только через существующую форму backend.
- При отсутствии ключа, ошибках сети или лимитах Groq работает fallback.
- Ключ задаётся локально через `Set-SneakChatGroqKey.ps1`; затем остановите сервер и запустите `Start-SneakChat.cmd -AIProvider groq`.
- Для `json_validate_failed` возможен один повтор при подтверждённом запасе квоты и времени. Для HTTP 429 повторов нет.

Проверка 20 октября 2026: 75 целевых локальных тестов с HTTP-моками; в отдельном реальном диалоге 10 из 10 обращений Groq приняты без 400/429. Один вопрос о цене обслужен напрямую backend. Это ограниченная проверка, не гарантия понимания любых сообщений. Реальное оформление ранее проверялось только на временной SQLite. Интеграция не добавляет выдуманные свойства обуви.

## Постоянный запуск

Без Codex и терминала: в папке проекта дважды щёлкните `Start-SneakChat.cmd` для магазина,
`Admin-SneakChat.cmd` для админки или `Stop-SneakChat.cmd` для остановки общего сервера.
Все три файла вызывают существующий `Start-SneakChat.ps1`. Повторный запуск открывает уже
работающий сервер на порту 8002. Обычный запуск использует автономный fallback без Groq.
После остановки или завершения процесса достаточно снова открыть `Start-SneakChat.cmd`.
Закрытие вкладки браузера не останавливает сервер. Для админки нужен настроенный пароль владельца.

На этом компьютере используются готовые `backend/.venv` и `frontend/dist`; Node.js и сборка
при обычном запуске не нужны. Виртуальное окружение связано с установленным Python в профиле
Accio: перенос папки на другой компьютер потребует отдельной настройки Python и зависимостей.

На рабочем столе используйте **SneakChat** для магазина и **SneakChat Admin** для админки.
Оба ярлыка вызывают один `Start-SneakChat.ps1` из этого проекта и используют один FastAPI-сервер.

- Магазин: http://127.0.0.1:8002/
- Админка: http://127.0.0.1:8002/admin
- Проверка сервера: http://127.0.0.1:8002/api/health

Из PowerShell в корне проекта:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Start-SneakChat.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Start-SneakChat.ps1 -View admin
```

Для запуска с уже настроенным Groq (при отсутствии ключа или ошибке API работает fallback):

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Start-SneakChat.ps1 -AIProvider groq
```

Ключ берётся из `GROQ_API_KEY` или защищённого Windows DPAPI-хранилища,
настроенного через `Set-SneakChatGroqKey.ps1 -Dialog`. Он не нужен для автономного fallback.
Groq требует интернета и доступной квоты. При повторном запуске режим уже работающего
сервера не меняется; для смены режима сначала остановите его.

Остановка магазина, чата и админки (оба Python-процесса штатного сервера):

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Start-SneakChat.ps1 -Stop
```

Команда проверяет принадлежность серверных процессов этому проекту и завершает их дерево.
Повторная остановка безопасна. Текущие запросы прерываются: останавливайте после завершения
работы с формами. База, каталог, фотографии и авторизация не удаляются и не пересоздаются.
Codex и открытое окно терминала для работы запущенного сервера не требуются.

Запуск использует существующий `backend/.venv`, React-сборку `frontend/dist` и абсолютный путь к базе.
Повторный запуск переиспользует сервер этого проекта. Если порт занят другим сервером, запуск прекращается без остановки чужих процессов.
FastAPI стартует с `--lifespan off`: существующая схема и каталог не пересоздаются, миграции и seed при обычном запуске не выполняются.
Если схему потребуется менять, это отдельная согласованная задача.
Консультант при таком запуске использует проверенный детерминированный fallback (`AI_PROVIDER=disabled`), без внешних AI-запросов.
Журналы: `outputs/server.stdout.log` и `outputs/server.stderr.log`.

## API

- `GET /api/health`
- `GET /api/products`
- `GET /api/products/{id}`
- `GET /api/products/search?brand=Nike&color=White&size=43&min_price=80&max_price=130&gender=Men&use_case=Running&feature=school` — параметры кроссовок, они переводятся конфигурацией каталога в атрибуты.
- `GET /api/products/search?attribute=storage:256GB&attribute=color:Black` — произвольные атрибуты любого каталога: код и значение. Эти условия ядро обрабатывает без специального кода.
- `POST /api/assistant/search` — подбор из простого текстового запроса.
- `POST /api/requests` — сохранение контактной заявки в локальную SQLite базу.
- `GET /api/requests` — список заявок для admin view.
- `PATCH /api/requests/{id}/status` — изменение статуса заявки (`new`, `contacted`, `completed`, `cancelled`).
- `DELETE /api/requests/{id}` — удаление заявки после подтверждения в admin view.
- `POST /api/chat` — диалог с контекстом по `session_id`; текущая гибридная интеграция возвращает `mode=groq`, а безопасный режим — `fallback`. Сохранена прежняя опциональная интеграция Ollama. У консультанта свободный ввод без навязанных quick-reply кнопок.

Параметр `size` возвращает только модели, у которых этот размер есть в наличии (`stock > 0`).

Пример: `{"message":"Белые Nike 43 размера до $120"}`.

Для chat endpoint: `{"session_id":"demo-user-1","message":"Потрібні Nike до $120","language":"uk"}`. Поле `language` принимает `ru` или `uk` и по умолчанию равно `ru`. Без настроенного LLM используется безопасный детерминированный fallback.

Диалог не требует идеального запроса: для расплывчатого сообщения он задаёт один короткий уточняющий вопрос. Если точного размера нет, показывает ближайшие доступные размеры; если бюджет слишком мал — только реальные модели немного выше указанной суммы. Все варианты по-прежнему проверяются через базу данных.

В продолжении диалога можно сменить бренд или цвет, указать категорию («для девушки», «для парня»), попросить «Покажи ещё» без повтора уже выданных карточек. Назначение модели (`Running`, `Walking`, `Training`, `Trail`, `Lifestyle`) хранится в SQLite: запросы «для бега», «для прогулок», «для зала» и «для трекинга» становятся настоящим фильтром по каталогу.

Для живых запросов каталог также хранит проверяемые теги `school`, `autumn` и `water_resistant`. Поэтому «для школы», «на осень» и «чтобы не промокали» подбираются только среди помеченных в SQLite моделей. Это свойства демонстрационного каталога, а не обещания, придуманные AI. Без доступной Ollama тот же сценарий продолжает работать через детерминированный fallback.

## Универсальный каталог

Товар (`Product`) состоит из общих полей: имя, бренд, категория, описание, базовая цена, изображение и признак активности. Всё, что зависит от категории, хранится атрибутами:

- `Attribute` — код, имя и тип значения (`enum`, `number`, `string`, `boolean`);
- `ProductAttribute` — значения уровня товара: цвет, назначение, объём памяти;
- `Variant` — вариант со своим артикулом, ценой и остатком;
- `VariantAttribute` — значения уровня варианта: размер, объём памяти версии.

Поиск работает по нормализованным условиям `ProductQuery(brand, category, attributes, min_price, max_price)`. Ядро (`catalog.py`) не знает ни одной оси конкретного каталога: атрибут фильтруется по коду и значению, значения подставляются параметрами, а не строкой SQL. Модель тоже не строит SQL — она возвращает пары «код атрибута → значение», а условия из них собирает ядро.

Кроссовки описаны конфигурацией `SNEAKER_CONFIG` в `catalog_rules.py`: какие есть оси, какие из них уровня варианта, как называются старые ключи фильтров (`use_case` → `purpose`, `feature` → `tags`) и в каком порядке ослаблять условия, когда по ним ничего не нашлось.

Проверка универсальности — в `backend/tests/test_universal_catalog.py`: товар `category="Phone"` с атрибутом `storage=256GB` находится по этому атрибуту, хотя в приложении нет ни одной строки про storage. Там же проверены несколько вариантов у товара, разные размеры, разные цвета, бренд вместе с динамическим атрибутом, несколько атрибутов сразу, отсутствующее значение, неизвестный код атрибута — и отдельный тест на то, что в ядре нет осей конкретного каталога.

Что остаётся специфичным для кроссовок: словарь и синонимы (`catalog_rules.py`), ценовые и размерные формулировки парсера, диалоговый каскад в `services/chat.py` («снять цвет → снять бренд → предложить ближайший размер → предложить чуть дороже»), тексты ответов, совместимый вид карточки товара в `services/products.py` и вёрстка фронтенда.

## Диалог SneakChat

SneakChat — специализированный продавец кроссовок: он ведёт диалог, а не фильтрует выдачу.

- **Помнит условия.** Бренд, назначение, цвет, пол, размер и бюджет живут в состоянии диалога, поэтому «Нужны кроссовки для школы» → «42» ищет `school + 42`, а не начинает поиск заново.
- **Меняет условие одной фразой.** «Давай Adidas» меняет бренд, сохраняя назначение и размер; «нет, максимум 100» заменяет бюджет, не оставляя старое значение активным.
- **Снимает условие.** «Бренд не важен», «любой цвет», «размер не учитывай», «без ограничения по цене», «не обязательно Nike», «покажи все» убирают соответствующее условие из состояния.
- **Не превращается в анкету.** Если данных достаточно для полезной выдачи, показываются товары; если не хватает одного критичного параметра, задаётся один короткий вопрос — обычно про размер.
- **Ослабляет условия прозрачно.** Когда точного совпадения нет, ответ прямо говорит, что было ослаблено, и при этом никогда не ослабляет размер и наличие: показывается только то, что реально есть в наличии.
- **Объясняет выбор.** У каждой карточки есть `match_reasons` — фразы, собранные только из данных каталога и фактически применённых условий: «размер 43 в наличии», «для бега», «укладывается в бюджет до $120». То, чего в каталоге нет, не придумывается.
- **Понимает продолжение.** «Покажи дешевле», «Другой цвет», «Похожие», «Другой бренд», «А 44 есть?» — эти подсказки приходят в ответе и работают как обычные фразы.
- **Честно отвечает про отсутствующее.** «Тёплые», «на лето», «розовые» не превращаются в фильтр: ассистент говорит, что такого признака в каталоге нет, и подбирает по остальным условиям.

## Optional Ollama

The LLM only extracts intent and filters; product facts always come from backend tools. Copy `.env.example` values into your environment: set `AI_PROVIDER=ollama`, `OLLAMA_BASE_URL=http://127.0.0.1:11434`, `OLLAMA_MODEL=qwen2.5:3b` and optionally `AI_DEBUG=true`. If Ollama is unavailable or returns invalid JSON, chat automatically uses the fallback.

Словарь у модели и у детерминированного парсера общий: он лежит в `backend/app/catalog_rules.py`. Оттуда же собирается лексикон промпта (`lexicon()`) и подписи в ответах, поэтому бренд, цвет, пол, назначение, тег или граница размера добавляются в одном месте.

Фильтр от модели применяется, только если значение есть в справочнике и модель приложила `evidence` — фразу из сообщения пользователя, на которую опирается фильтр. Фраза обязана присутствовать в сообщении, для размера и цены содержать цифру, для категорий состоять из содержательного слова и не начинаться с формулировки другого фильтра («белые» не подтверждают бренд или пол; «бел» не подтверждает чёрный цвет). Поэтому модель может поставить фильтр, которого не видит регулярный парсер (опечатка, разговорная форма, «тёмные» → `Black`), но не может опереться на служебное слово или на противоречащую фразу. Значения модели без собственного признака в тексте действуют один ход и не переносятся в следующие сообщения.

Проверка подтверждения формальная: она гарантирует опору на слова пользователя, но не смысл. Если модель выберет произвольное содержательное слово из сообщения, проверка пройдёт — такое ограничение честнее принять, чем утверждать полноценную проверку смысла регулярками. Отрицания («не белые») и признак, спрятанный внутри другого слова, не понимает ни парсер, ни контракт с моделью.

Алиасы словаря сопоставляются с начала слова и начиная с самого длинного: «серебристые» — это `Silver`, а не `Grey`, а «пробежка» не становится бежевой из-за «беж».

Цены проверяются границами (`PRICE_MIN`/`PRICE_MAX`) и действуют один ход, если бюджет не назван в тексте.

`intent` модель возвращает, но он пока используется только в отладочном логе (`AI_DEBUG=true`): выборку определяют фильтры, а ветки ответа — детерминированная логика.

## Надёжность AI и grounding

Каждое значение, которое предлагает модель, проверяется до поиска
(`backend/app/ai/validation.py`): тип, границы оси и наличие в живых данных каталога. Лишний
ключ в ответе модели или неизвестный `intent` означает, что разбор не используется целиком.
Проверка идёт по сырому ответу, до приведения типов, поэтому молчаливое превращение «до 120» в
отсутствующее значение невозможно.

Отрицания разбираются детерминированно в обе стороны — «не Nike», «только не белые»,
«не для бега», «не 43», а также «белые не нужны» и «43 не нужен». Исключённое значение вырезается
до положительного разбора, поэтому «только не Nike» не превращается в фильтр по Nike. Ядро
каталога умеет выражать исключения (`exclude_brand`, `exclude_attributes`), и они сохраняются при
ослаблении выдачи, в «похожих» и на следующих ходах; снимаются только явно — «цвет не важен»,
«покажи все», «начать заново».

Перед отправкой ответ проходит страховку (`backend/app/ai/grounding.py`): каждый товар
сверяется с текущим состоянием базы, товар без подтверждённого пояснения не показывается, а
сумма, которую не подтверждает ни одна цена и ни одно условие, не попадает в текст — ответ
пересобирается без сумм.

Любой сбой провайдера — недоступная модель, timeout, битый JSON, пустой или нестроковый ответ —
превращается в `ProviderUnavailable` и безопасный детерминированный разбор. Ни один из пятнадцати
проверенных сценариев сбоя не даёт HTTP 500 и не показывает пользователю внутреннюю ошибку.

Тесты: `Ran 249 tests ... OK`. Подробности и известные ограничения —
`STAGE5_GROUNDING_RELIABILITY_REPORT.md`.

## Товарный контекст и закрытый словарь

SneakChat понимает запросы о кроссовках через **закрытый доменный словарь** русского и украинского
языка. Морфологического анализа нет: разбор свободного текста совпадает только с целым словом или
целой объявленной фразой, поэтому список форм пополняется явно, а не выводится правилами.

Перед разбором работает доменный gate: если в сообщении есть слово вне домена или в самом сообщении
нет признака запроса, сообщение не считается запросом каталога и не меняет состояние диалога — ни
условия, ни режим просмотра, ни сохранённую выдачу, ни выборку. Поэтому обычный текст вроде
«пума на дереві», «покажи все новости за неделю», «мне 43 года» или «Купити квиток на 43 місце»
фильтров не создаёт.

Отрицания («не Nike», «белые не нужны»), снятие условий («бренд не важен», «будь-який бренд»),
короткие продолжения («43», «красные», «до 100») и «покажи похожие» работают как раньше.
«Похожие» используют временное переопределение поиска и не переписывают условия пользователя.

Тесты: `Ran 342 tests ... OK`. Подробности, история тринадцати независимых аудитов и известные
ограничения — в `STAGE5_GROUNDING_RELIABILITY_REPORT.md`.

## Контракт продолжения диалога

В активном сеансе подбора короткие реплики со значениями считаются продолжением запроса: «43» —
размер, «Puma» — бренд, «красные» — цвет, «до 100» — бюджет, «не белые» — исключение, «дешевле»,
«похожие», «покажи ещё» — команда продолжить. Это осознанный продуктовый контракт: покупатель ведёт
разговор короткими репликами.

Значение никогда не додумывается: «это не мой размер» оставляет условия прежними. Вне товарного
контекста обычный текст не меняет состояние, не запускает поиск, не сбрасывает фильтры и не
возвращает выдачу. Gate — детерминированная доменная логика без NLP-классификатора и без LLM.

Этап 5 закрыт: `Ran 342 tests ... OK`, сборка фронтенда зелёная. Решение по границе gate —
раздел «Gate ambiguity decision» в `STAGE5_GROUNDING_RELIABILITY_REPORT.md`.

## Этап 6 — товарный интерфейс

Карточки товаров в чате и каталоге, «почему подходит», размеры и наличие, быстрые действия, экран
деталей, сравнение моделей, честный ответ «точного совпадения нет», состояния загрузки и ошибок,
мобильная адаптация. Интерфейс ничего не решает сам: `POST /api/chat` возвращает `reply`,
`products`, `filters`, `suggestions`, `mode`, `needs_clarification`, а фронтенд только отображает.
Над карточками показывается строка «Условия подбора: …» по полю `filters` ответа; товар дороже
условия получает пометку «выше бюджета на $N»; остаток по каждому размеру виден прямо в плашке
размера, а не только при наведении.

Что изменилось в ответах backend: «покажи подешевле» прямо говорит, если дешевле показанного ничего
нет; при полном отсутствии моделей названы реальные рычаги («Можно ослабить: бренд, бюджет или
размер») и ближайшие размеры, которые есть в наличии, а кнопки снимают именно эти условия;
противоречивая формулировка «с теми же условиями … без ограничений по бренду, цвету и цене»
заменена на «Бренд, цвет и цену не учитываю: …, оставляю условия: …».

Изображения товаров — реальные фото конкретных моделей, по файлу на модель:
`frontend/public/images/sneakers/{ключ}.jpg`, ключ считается на бэкенде из бренда и названия
(`nike-air-max-pulse`, `adidas-samba-og`), поэтому модели одного цвета больше не делят одну картинку.
В базе хранится только ключ, поэтому каталог и миграции не менялись; если фото нет, показывается
`fallback.svg`. Снимки взяты со страниц брендов и ретейлеров — это чужие изображения с товарными
знаками: для демо допустимо, для настоящего магазина нужны свои фото или дилерский фотобанк.
У 12 из 27 моделей источник мелкий (180–683 px) — такие карточки выглядят мягко. E2E-тест проверяет,
что у каждой модели каталога есть файл изображения.
